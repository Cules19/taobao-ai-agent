# 选物 2.0：上线、运行原理与验收

本版本面向有访问凭据的单机私有试点。商品、价格、库存、优惠券、物流均为虚构数据。部署后用户可以体验导购，不会产生真实订单或支付。

## 1. 本机试用

在 PyCharm Terminal 运行：

```powershell
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
.\.venv\Scripts\python.exe run_local.py
```

终端会提示隐藏输入模型 Key；默认读取 DeepSeek。访问 http://127.0.0.1:8000/。后端保存会话；刷新后从左栏继续。新建对话不会删除旧记录；点历史旁的 × 才删除。另一浏览器或无痕窗口看不到当前记录。请勿输入个人信息，消息会发给你所配置的模型服务商。

## 2. 部署到服务器

准备一台 Linux 主机、Docker Engine 和 Compose v2、一个指向主机的域名、可用的模型服务与费用额度。开放入站 80/443 给 Caddy，模型服务需要出站 HTTPS。应用的 8000 端口仅容器内部可达。

1. 在目标主机检出你要运维的提交，复制 `.env.example` 为 `.env`，设为仅部署账号可读（`chmod 600 .env`）。
2. 填写 `SHOP_DOMAIN`（只填域名），独立生成 `SHOP_SESSION_SECRET`（例如 `openssl rand -hex 32`），填模型 Key、模型名和兼容基础 URL。
3. 设置私有访问用户名。在交互式终端生成密码哈希：`docker run --rm -it caddy:2-alpine caddy hash-password`。将生成的哈希用单引号包住填入 `SHOP_ACCESS_PASSWORD_HASH`，避免其中的美元符号被 Compose 展开。不要在命令行参数中写明文密码。
4. 核对配置后启动：

```sh
docker compose config --quiet
docker compose up -d --build --wait
docker compose ps
docker compose logs --tail=80 app edge
```

5. 从外部访问你的 HTTPS 域名。未登录应返回 401；提供试点凭据后应显示新界面。认证后访问 `/readyz` 应返回 `{"status":"ready"}`，`/docs` 应为 404。用实际模型运行第 5 节的用例。就绪探针读 SQLite，不调用计费模型，因此不能代替真实联调。

生产模式拒绝非 HTTPS 的模型地址、缺少模型配置和短会话密钥。通过浏览器发起的写请求必须来自配置的 HTTPS Origin。默认反向代理使用 HTTP Basic 作为试点入口保护，请只给受邀人员提供密码；浏览器 Cookie 负责会话隔离，不能跨设备找回账号。给全量客户开放前，应改用逐用户身份认证及独立限额。

## 3. 数据流与文件

| 文件 | 职责 |
| --- | --- |
| `run_local.py` | 本地启动器，隐藏输入模型 Key；开发模式只监听本机。 |
| `main.py` | 首页、聊天、会话历史、删除接口和探针；先识别用户和扣额度，再调用 Agent，返回请求 ID。 |
| `runtime.py` | 读取模型和试点的运行配置，检查生产启动条件。 |
| `boundary.py` | 给浏览器签发 HttpOnly 会话 Cookie，约束写请求来源、JSON 大小及页面可加载资源。 |
| `storage.py` | SQLite 中保存对话、收藏和计数。对话按 Cookie 身份查询；同一对话使用数据库租约避免并发写覆盖。 |
| `sessions.py` | 一次 Agent 执行用的会话结构；模型上下文保留最近 6 轮完整消息。 |
| `agent.py` | 把模型的 `tool_calls` 交给工具注册表，按 `tool_call_id` 将结果回填，再请求最终回复。 |
| `model_client.py` | 以环境变量构建 OpenAI 兼容 SDK 客户端。 |
| `shop_tools.py` / `catalog.py` | 工具定义与校验、耗时日志、业务查询及收藏操作。数据来自 `demo_data/`。 |
| `web/` | 原生工作台页面、响应式配色及插画、聊天/历史/详情/收藏交互。服务端文本以纯文本渲染。 |
| `Dockerfile` / `compose.yaml` / `deploy/Caddyfile` | 非 root 应用容器、健康检查、持久卷、HTTPS 和私有入口。 |
| `requirements-prod.txt` / `requirements.txt` | 固定的生产依赖，以及用于开发的 pytest。 |
| `test/` / `.github/workflows/verify.yml` | 业务与协议回归、会话与额度校验；CI 验证 Python、JS 和容器构建。 |

请求链路：浏览器 → Caddy → FastAPI → 站点及访客额度 → 读取会话 → 模型选择工具 → Python 查询 JSON → 回填结果 → 保存 SQLite → 浏览器展示回复和商品卡。

## 4. 运维

- 默认同一浏览器每分钟 12 条、站点每分钟 120 条、每 UTC 日 600 条。计数持久化，失败请求也计入；单轮最多 4 次模型请求。按实际预算调低额度，同时在模型服务商侧设置费用上限。访客额度依赖浏览器身份，站点额度是兜底。
- 默认只展示每个对话最近 30 轮；7 天不活跃的对话将不可见，下一次正常聊天触发物理清理。SQLite 和备份都应当作为可能包含用户消息的数据保护，设置磁盘加密与备份到期策略。浏览器清掉 Cookie、生产密钥轮换后，原身份将无法读取旧会话。
- 查故障时用响应头 `X-Request-ID` 对照 `chat_failure` 和耗时日志。观察 429、503、模型账户余额、进程重启和磁盘余量。模型服务不可达会返回清晰错误，页面保留输入便于重试。
- 备份不要直接复制运行中的 SQLite 文件。用下面的可写目录接收 SQLite 在线备份；把备份保护好。还原需停止应用，将已有卷离线备份，再用确认可用的备份恢复，检查卷属主 10001 后重启。建议先在隔离环境演练。

```sh
umask 077
docker compose exec -T app python -c "import sqlite3; sqlite3.connect('/state/store.sqlite3').backup(sqlite3.connect('/tmp/shop-backup.sqlite3'))"
docker compose cp app:/tmp/shop-backup.sqlite3 ./shop-backup.sqlite3
docker compose exec -T app python -c "from pathlib import Path; Path('/tmp/shop-backup.sqlite3').unlink()"
```

推荐保留前一个通过验收的提交和对应镜像，更新时先备份再构建。当前是单节点 SQLite，不能把同一数据卷挂到多台机器作为共享数据库；多副本、高可用、逐用户鉴权、正式目录/订单接入、容量和安全评估需要目标环境验收。

## 5. 发布验收

1. 执行 `python -m pytest -q`，确认原有业务、新增权限、持久化、额度与请求边界测试都通过。测试替换模型网络响应；正式运行不会使用模拟模型。
2. 真实模型中询问“200 元以内的蓝牙耳机，按销量排序”，应返回 P102、P101、P103；再问“第一款有蓝色吗？”，并检查实际工具日志。
3. 点喜欢，看收藏计数；刷新页面，从历史打开，检查收藏仍在。用无痕窗口确认隔离；测试删除和 429 恢复。
4. 试查“179 元的耳机优惠券”和演示订单 DEMO1001；无结果时要澄清或提示。试验模型故障时网页给出错误且可重试。
5. 检查域名的 HTTPS、入口认证、容器健康和备份恢复；在目标主机做容量检查后再交付给试点用户。

设计参考：[FastAPI 官方全栈模板](https://github.com/fastapi/full-stack-fastapi-template) 的部署结构和探针，以及 [Open WebUI](https://github.com/open-webui/open-webui) 的响应式对话工作区。项目使用自己的实现和视觉设计。
